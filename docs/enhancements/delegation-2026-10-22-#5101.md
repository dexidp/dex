## Summary

Dex's token exchange ([RFC 8693]) accepts a `subject_token` and issues a Dex token for that subject.
This is impersonation in the sense of [RFC 8693 Section 1.1]: the issued token says nothing about who presented it.
This DEP adds delegation to the same grant.
A confidential client may also present an `actor_token`; Dex verifies it through a connector and issues one token whose `sub` is the subject and whose `act` claim names the actor.
When the subject token carries a `may_act` claim, Dex enforces it.
Delegation is off unless an operator enables it per client, and every ambiguous case fails closed.

[RFC 8693]: https://www.rfc-editor.org/rfc/rfc8693.html
[RFC 8693 Section 1.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1

## Context

- [#5101] is the feature request this DEP answers.

- [DEP #2812] introduced token exchange and listed `actor_token` and `actor_token_type` as "OPTIONAL - unused".
  Its Future Improvements say they "can be checked / validated if a suitable use case is determined".
  This DEP supplies the use case and the validation.
- [#4910] split `/token` into per-grant handlers (`server/grants`) and [#4893] introduced `tokens.Issuer`.
  Delegation is added inside the token-exchange grant and the issuer, with no change to the other grants.
- [#4619] lets a connector be restricted to the grants it serves (`grantTypes`).
  An actor connector is a connector restricted to token exchange.
- [#4780] added the structured success log for token exchange; this DEP extends that line.
- [#4397] reports that id_token exchanges skip the `aud` check in the oidc connector.
  Delegation checks the actor token's audience in the grant, independent of that connector behaviour.
- [#3546] asks to refuse token exchange for public clients. Delegation refuses public clients from the start, the same rule `client_credentials` applies.
- [DEP #4600] / [#4611] (ID-JAG) extend token exchange with a per-client policy under `oauth2.tokenExchange`.
  The configuration proposed here sits in the same block.

Use case. An agent runtime runs autonomous workloads on behalf of signed-in people.
Each workload has its own short-lived identity, a JWT minted by the runtime's issuer with a per-session subject.
A gateway in front of protected backends holds the person's Dex token and the workload's actor JWT.
Backends need one bearer token that says "this person, acting through this workload", so they can authorize as the person, audit the workload, and tell a human call from an agent call.
Today the gateway must either forward the person's token alone (the workload becomes invisible) or run its own token service (a second issuer the backends must trust).
RFC 8693 delegation at the identity provider is the standard answer.

## Motivation

### Goals/Pain

- Accept `actor_token` and `actor_token_type` on the token-exchange grant ([RFC 8693 Section 2.1]), verified through a connector like the subject token.
- Issue the `act` claim ([RFC 8693 Section 4.1]) in ID tokens and access tokens, with nesting when the subject token already carries `act`.
- Enforce `may_act` ([RFC 8693 Section 4.4]) when the subject token carries it.
- Per-client, operator-controlled enablement with fail-closed defaults.
- Keep the impersonation path byte-for-byte as it is for clients that send no actor.

### Non-goals

- Issuing `may_act`. Dex has no source for "who may act for this subject"; see Future Improvements.
- Actor tokens of type `access_token`. The oidc connector verifies those through userinfo, so the token's own `aud`, `exp` and `may_act` are not available.
- Per-client fields on the stored client object (`storage.Client`). See Alternatives.
- Refresh tokens for delegated tokens. Token exchange returns a single token today and keeps doing so.
- Resource and audience parameters of RFC 8693 Section 2.1.1, out of scope since DEP #2812.

[RFC 8693 Section 2.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-2.1
[RFC 8693 Section 4.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1
[RFC 8693 Section 4.4]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.4

## Proposal

### User Experience

Configuration. The actor's issuer is a connector restricted to token exchange. Delegation is enabled per client:

```yaml
connectors:
  - type: oidc
    id: agent-runtime
    name: Agent runtime
    config:
      issuer: https://issuer.agents.example.internal
      userNameKey: sub          # machine tokens carry no "name" claim
    grantTypes:
      - urn:ietf:params:oauth:grant-type:token-exchange

oauth2:
  tokenExchange:
    delegation:
      - clientID: gateway
        actorConnectors: [agent-runtime]
        # actorAudiences: [https://dex.example.com]   # optional; the Dex issuer URL is always accepted
        # requireMayAct: true                         # default; set false to allow subjects without may_act

staticClients:
  - id: gateway
    secret: ...
    trustedPeers: [backend-api]
```

Request. The client adds the actor token, its type and the connector that verifies it:

```sh
curl https://dex.example.com/token \
  --user gateway:secret \
  --data-urlencode grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  --data-urlencode connector_id=dex-self \
  --data-urlencode subject_token=$PERSON_TOKEN \
  --data-urlencode subject_token_type=urn:ietf:params:oauth:token-type:id_token \
  --data-urlencode actor_connector_id=agent-runtime \
  --data-urlencode actor_token=$WORKLOAD_TOKEN \
  --data-urlencode actor_token_type=urn:ietf:params:oauth:token-type:jwt \
  --data-urlencode scope="openid audience:server:client_id:backend-api" \
  --data-urlencode requested_token_type=urn:ietf:params:oauth:token-type:access_token
```

Response. One token, as today. Its payload:

```json
{
  "iss": "https://dex.example.com",
  "sub": "CgdwZXJzb24xEghkZXgtc2VsZg",
  "aud": ["backend-api", "gateway"],
  "azp": "gateway",
  "exp": 1761150000,
  "act": {
    "iss": "https://issuer.agents.example.internal",
    "sub": "workload/session-7f3a"
  }
}
```

A backend reads `sub` for authorization and `act` for audit; per RFC 8693 Section 4.1 it considers only the top-level claims and the outermost `act`.

Errors. All are `400 invalid_request` with a description, unless the client is unknown or the token does not verify:

| Case | Response |
| --- | --- |
| `actor_token` without `actor_token_type`, or the reverse | `invalid_request`, "actor_token and actor_token_type must be sent together" |
| `actor_token_type` is `access_token` | `invalid_request`, "actor_token_type not supported for delegation" |
| `actor_token` on any other grant | `invalid_request` |
| client has no `delegation` entry | `invalid_request`, "delegation is not enabled for this client" |
| client is public | `invalid_request`, "delegation requires a confidential client" |
| `actor_connector_id` missing or not in `actorConnectors` | `invalid_request` |
| actor token does not verify | `401 access_denied` (same as a bad subject token) |
| actor `aud` names neither the Dex issuer nor an `actorAudiences` entry | `invalid_request`, "actor token audience does not include this server" |
| subject `may_act` present, actor does not match | `invalid_request`, "actor is not authorized by the subject token's may_act claim" |
| subject has no `may_act` and `requireMayAct` is true | `invalid_request`, "subject token carries no may_act claim" |
| resulting `act` chain deeper than 10 | `invalid_request`, "delegation chain too deep" |
| subject token carries `act` and no `actor_token` is sent | `invalid_request`, "subject token is delegated; present an actor_token" |

### Implementation Details/Notes/Constraints

Request (`server/grants/grants.go`). `Request` gains `ActorToken`, `ActorTokenType`, `ActorConnectorID`. `Handler.dispatch` rejects any of them on a grant other than token exchange.

Verified claims (`connector/connector.go`). `TokenIdentityConnector` returns an `Identity` only; the grant never sees `iss`, `aud`, `exp`, `may_act` or `act` of either token. Add an optional interface:

```go
// TokenClaimsConnector verifies a token and returns the identity together with
// the verified claims the identity was derived from.
type TokenClaimsConnector interface {
	TokenIdentityClaims(ctx context.Context, tokenType, token string) (Identity, map[string]any, error)
}
```

The oidc connector implements it (the claims are already decoded in `createIdentity`) and accepts `urn:ietf:params:oauth:token-type:jwt` next to `id_token` for exchanges. The mock connector implements it with a configurable claims map. A connector without it can still serve impersonation; a delegation request through it is refused.

Policy (`cmd/dex/config.go`, `server/grants/delegation.go`):

```go
type DelegationPolicy struct {
	ClientID        string   `json:"clientID"`
	ActorConnectors []string `json:"actorConnectors"`
	ActorAudiences  []string `json:"actorAudiences"`
	RequireMayAct   *bool    `json:"requireMayAct"` // nil means true
}
```

Loaded under `oauth2.tokenExchange.delegation`, validated at startup (`actorConnectors` must name configured connectors), passed to `grants.Handler`. The actor connector goes through the Handler's existing `resolveConnector`, so the client's `allowedConnectors` and the connector's `grantTypes` apply to it exactly as to the subject connector.

Grant (`server/grants/tokenexchange.go`), after the subject is verified:

```go
if req.ActorToken == "" {
	if subjectClaims["act"] != nil {
		return invalidRequest("subject token is delegated; present an actor_token")
	}
	// impersonation, unchanged
}
policy, ok := g.delegation[client.ID]
if !ok || client.Public { ... }
actorConn := g.resolveConnector(ctx, req.ActorConnectorID, client, grantType) // + membership in policy.ActorConnectors
actorIdentity, actorClaims, err := actorConn.(connector.TokenClaimsConnector).TokenIdentityClaims(ctx, req.ActorTokenType, req.ActorToken)
checkAudience(actorClaims["aud"], g.issuerURL, policy.ActorAudiences)
checkMayAct(subjectClaims["may_act"], actorClaims, policy.RequireMayAct)
act := &tokens.ActorClaims{Issuer: actorClaims["iss"], Subject: actorClaims["sub"], Act: nestedFrom(subjectClaims["act"])}
if act.Depth() > maxActDepth { ... }
auth.Act = act
auth.ExpiresAt = min(subjectExp, actorExp) // zero keeps the configured lifetime
```

`may_act` matching follows RFC 8693 Section 4.4: `sub` must match, and `iss` must match when `may_act` carries one. Other claims inside `may_act` are not compared in this version.

Claims (`server/tokens/claims.go`, `issuer.go`):

```go
type ActorClaims struct {
	Issuer  string       `json:"iss,omitempty"`
	Subject string       `json:"sub"`
	Act     *ActorClaims `json:"act,omitempty"`
}
```

`IDTokenClaims` and `tokens.Authorization` gain `Act *ActorClaims`; `Authorization` gains `ExpiresAt time.Time`. `SignIDToken` writes `act` and caps `exp`. Access tokens are minted by the same function, so both token types carry `act`. `act` is never copied into `federated_claims`. Introspection passes `act` through (RFC 7662 allows additional members).

Scopes and audience are untouched: the actor contributes no scope and no audience; `aud` comes from the client and its cross-client scopes as today.

### Observability

The existing "token exchange successful" log line gains `actor_connector_id`, `actor_iss`, `actor_sub`, `may_act_enforced` and `act_depth`. Refusals log the reason with the same keys. Raw tokens are never logged.

### Risks and Mitigations

- Actor token replay from another relying party. An actor token minted for some other audience must not turn into a Dex delegation. The grant requires the actor's `aud` to name the Dex issuer or an operator-listed audience; the check lives in the grant and does not depend on the connector's audience handling (#4397).
- Actor substitution. A client could pair a person's token with any token its actor connector verifies. Two gates: the operator's `actorConnectors` list says which issuers may act for that client at all, and `may_act`, when the subject token carries it, binds the subject to one actor. `requireMayAct` defaults to true, so a deployment that enables delegation without `may_act` does so explicitly.
- Privilege widening. The actor adds nothing: no scopes, no audiences, no groups. The issued token's lifetime is the shortest of the configured lifetime, the subject token and the actor token.
- Chain depth. Nested `act` is bounded at 10 levels; deeper requests are refused rather than truncated.
- Confused deputy through a public client. Public clients cannot delegate; a public client's secret is public, so anything holding two tokens could mint a composite token in its name.
- Laundering a delegated token. A subject token that carries `act` cannot be exchanged without an actor: dropping the chain would turn a delegated token into an impersonation token, and copying it forward would assert an actor that did not authenticate in this request (RFC 8693 Section 4.1 makes the outermost `act` the current actor).
- Personal data in logs. The log line carries identifiers (`actor_sub`, existing `user_id`, `email`), as the current exchange log does, and never tokens.
- Breaking change: none. Clients that send no actor parameters see the same behaviour and the same tokens. The new connector interface is optional.

### Alternatives

- Fields on `storage.Client`. First-class per-client fields would reach clients created over gRPC and the Kubernetes CRD, but every storage backend changes (ent schema and SQL migration, Kubernetes types, `api.proto`, conformance tests), as `allowedConnectors` did across about 35 files. A server-level policy keyed by client ID has the same effect for static clients, which is where token-exchange clients are configured today, and can move into the client object later without changing semantics.
- Verify the actor token in the handler with a JWKS fetch. Shorter, but it bypasses connector policy (`allowedConnectors`, `grantTypes`, custom CAs, discovery overrides) that the subject path already enforces. Delegation reuses the connector path for both tokens.
- Let the gateway run its own token service. Backends then trust a second issuer, and the person's identity provider loses sight of the delegation. RFC 8693 places this at the authorization server.
- Do nothing. Deployments keep forwarding person tokens alone, or minting composite tokens outside Dex. DEP #2812 left this open for a use case; the use case exists.

## Future Improvements

- Issuing `may_act`: from a consent step, a connector-supplied claim, or a policy source such as the CEL work in DEP "CEL integration" (#4601). Today's enforcement is designed so issuance can be added without changing the exchange.
- Actor tokens of type `access_token`, verified through introspection or userinfo of the actor's issuer, once the connector can return the token's verified claims for that type.
- Allowing `jwt`-type subject tokens generally, beyond exchanges, and letting the new `jwt` connector (#5083) serve as an actor connector by implementing `TokenClaimsConnector`.
- Comparing further identity claims inside `may_act` (RFC 8693 Section 4.4 allows claims beyond `sub` and `iss`).
