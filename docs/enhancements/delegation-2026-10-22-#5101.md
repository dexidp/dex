## Summary

Dex's token exchange ([RFC 8693]) accepts a `subject_token` and issues a Dex token for that subject.
This is impersonation in the sense of [RFC 8693 Section 1.1]: the issued token says nothing about who presented it.
This DEP adds delegation to the same grant.
A confidential client may also present an `actor_token`; Dex verifies it through a connector and issues one token whose `sub` is the subject and whose `act` claim names the actor.
When the subject token carries a `may_act` claim, Dex enforces it.
Delegation is off unless an operator enables it per client, and clients without it see no change.

[RFC 8693]: https://www.rfc-editor.org/rfc/rfc8693.html
[RFC 8693 Section 1.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1

## Context

- [#5101] is the feature request this DEP answers.
- [DEP #2812] introduced token exchange and listed `actor_token` and `actor_token_type` as "OPTIONAL - unused".
  Its Future Improvements say they "can be checked / validated if a suitable use case is determined".
  This DEP supplies the use case and the validation.
- [#4910] split `/token` into per-grant handlers (`server/grants`) and [#4893] introduced `tokens.Issuer`.
  Delegation is added inside the token-exchange grant, the grant handler and the issuer, with no change to the other grants.
- [#4619] lets a connector be restricted to the grants it serves (`grantTypes`).
  An actor connector is a connector restricted to token exchange.
- [#4397] reports that id_token exchanges skip the `aud` check in the oidc connector.
  Delegation checks the actor token's audience in the grant, independent of that connector behaviour.
- [#3546] asks to refuse token exchange for public clients. Delegation refuses public clients from the start.
- [DEP #4600] / [#4611] (ID-JAG, open) propose a per-client policy under `oauth2.tokenExchange`.
  That block does not exist yet; this DEP introduces it with a `delegation` key, compatible with the ID-JAG proposal whichever lands first.

Use case. An agent runtime runs autonomous workloads on behalf of signed-in people.
Each workload has its own short-lived identity, a JWT minted by the runtime's issuer with a per-session subject.
A gateway in front of protected backends holds the person's token and the workload's actor JWT.
Backends need one bearer token that says "this person, acting through this workload", so they can authorize as the person and audit the workload.
Today the gateway must either forward the person's token alone (the workload becomes invisible) or run its own token service (a second issuer the backends must trust).

## Motivation

### Goals/Pain

- Accept `actor_token` and `actor_token_type` on the token-exchange grant ([RFC 8693 Section 2.1]), verified through a connector like the subject token.
- Issue the `act` claim ([RFC 8693 Section 4.1]) in ID tokens, access tokens and introspection responses.
- Enforce `may_act` ([RFC 8693 Section 4.4]) when the subject token carries it.
- Per-client, operator-controlled enablement, including the audiences a delegated token may carry; no change for other clients.
- Exchange Dex-issued subject tokens, verified with Dex's own keys, keeping their `sub`.

### Non-goals

- Issuing `may_act`. Dex has no source for "who may act for this subject".
- Delegation chains. A subject token that already carries `act` is refused for delegation; see Future Improvements.
- Impersonation through a delegating client. A client with a `delegation` entry always presents an actor; impersonation uses another client.
- `access_token` as actor or subject token type for delegation. The oidc connector verifies those through userinfo, so the token's own `aud`, `exp`, `act` and `may_act` are not available.
- Per-client fields on the stored client object (`storage.Client`). See Alternatives.
- Refresh tokens for delegated tokens. Token exchange returns a single token today and keeps doing so.

[RFC 8693 Section 4.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1
[RFC 8693 Section 4.4]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.4

## Proposal

### User Experience

Configuration. The actor's issuer is a connector restricted to token exchange. Delegation is enabled per client:

```yaml
connectors:
  - type: oidc
    id: corp                    # the connector people sign in through
    # ...
  - type: oidc
    id: agent-runtime
    name: Agent runtime
    config:
      issuer: https://issuer.agents.example.internal
    grantTypes:
      - urn:ietf:params:oauth:grant-type:token-exchange

oauth2:
  tokenExchange:
    delegation:
      - clientID: gateway
        actorConnectors: [agent-runtime]
        audiences: [backend-api]  # backends that read the act claim

staticClients:
  - id: gateway
    secret: ...
  - id: backend-api
    # ...
    trustedPeers: [gateway]     # lets gateway request audience:server:client_id:backend-api
```

The actor connector only verifies the actor token's signature, issuer and expiry and returns its claims.
Its identity mapping (`userNameKey`, `email`, `groups`, userinfo) is not used, so a machine token needs no `name` or `email` claim.

Request. The client adds the actor token, its type and the connector that verifies it.
The subject token here is one Dex issued to the gateway, so no `connector_id` is sent and Dex verifies it with its own keys:

```sh
curl https://dex.example.com/token \
  --user gateway:secret \
  --data-urlencode grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  --data-urlencode subject_token=$PERSON_ID_TOKEN \
  --data-urlencode subject_token_type=urn:ietf:params:oauth:token-type:id_token \
  --data-urlencode actor_connector_id=agent-runtime \
  --data-urlencode actor_token=$WORKLOAD_TOKEN \
  --data-urlencode actor_token_type=urn:ietf:params:oauth:token-type:jwt \
  --data-urlencode scope="openid audience:server:client_id:backend-api" \
  --data-urlencode requested_token_type=urn:ietf:params:oauth:token-type:access_token
```

Response. One token, as today:

```json
{
  "iss": "https://dex.example.com",
  "sub": "CgdwZXJzb24xEgRjb3Jw",
  "aud": ["backend-api", "gateway"],
  "azp": "gateway",
  "exp": 1761150000,
  "act": {
    "iss": "https://issuer.agents.example.internal",
    "sub": "workload/session-7f3a"
  }
}
```

`sub` is the subject token's `sub` unchanged: a Dex-issued subject token is verified with Dex's keys and re-issued for the identity encoded in it. With `connector_id`, the subject token is verified by that connector as today and `sub` encodes its user ID and the connector.
A backend reads `sub` for authorization and `act` for audit. Only the audiences in the client's `audiences` list may be requested, because a consumer that does not read `act` would serve the token as the person alone.

Errors. Delegation refusals are `400 invalid_request` with a description, as RFC 8693 Section 2.2.2 requires for invalid or policy-refused actor tokens:

| Case | Description |
| --- | --- |
| `actor_token` and `actor_token_type` not sent together | "actor_token and actor_token_type must be sent together" |
| `actor_token` on any other grant | "actor_token is only valid for token exchange" |
| subject token not issued to the requesting client (`aud`) | "subject token audience does not include this client" |
| client has no `delegation` entry, or is public, and sends `actor_token` | "delegation is not enabled for this client" |
| delegating client sends no `actor_token` | "this client must present an actor_token" |
| `connector_id` names an actor connector (any client) | "connector only verifies actor tokens" |
| unsupported actor or subject token type | "token type not supported for delegation" |
| a connector that cannot return verified claims | "subject connector does not support delegation" / "actor connector does not support delegation" |
| actor connector not in the client's `actorConnectors` | "actor connector not allowed for this client" |
| actor token does not verify | "invalid actor_token" |
| actor `aud` does not include the client ID | "actor token audience does not include this client" |
| subject token carries `act` | "delegated subject tokens are not supported" |
| `may_act` present and not satisfied | "actor is not authorized by the subject token's may_act claim" |

A cross-client audience outside the client's `audiences` is refused with `400 invalid_target` ([RFC 8693 Section 2.2.2]), description "audience not allowed for delegation".

[RFC 8693 Section 2.2.2]: https://www.rfc-editor.org/rfc/rfc8693.html#section-2.2.2

An actor connector outside the client's `allowedConnectors`, or without the token-exchange grant type, is refused by the existing connector check with its existing `invalid_grant` / `invalid_request` errors.

### Implementation Details/Notes/Constraints

Request and connector resolution (`server/grants/grants.go`). `Request` gains `ActorToken`, `ActorTokenType`, `ActorConnectorID`; `dispatch` rejects them on other grants.
`dispatch` resolves the actor connector with the same `resolveConnector` it uses for the subject connector, before `Authorize`, so the client's `allowedConnectors` and the connector's `grantTypes` apply to it.
The token-exchange grant receives it next to the subject connector and checks membership in `policy.ActorConnectors`.

Verified claims (`connector/connector.go`). `TokenIdentityConnector` returns an `Identity` only, so the grant never sees `aud`, `exp`, `may_act` or `act`. Add an optional interface:

```go
// TokenClaimsConnector verifies a signed token and returns the claims of the
// token itself, without userinfo or claim mapping applied.
type TokenClaimsConnector interface {
	TokenClaims(ctx context.Context, tokenType, token string) (map[string]any, error)
}
```

The oidc connector implements it for `id_token` and `jwt` with the provider's verifier and no client ID check, and never calls userinfo.
Delegation requires it on both connectors; the subject connector also keeps serving `TokenIdentity` for the subject's identity. Impersonation does not use it.

Dex-issued subject tokens (`server/tokens`, `server/grants/tokenexchange.go`). Without `connector_id`, the grant verifies the subject token with Dex's own signing keys (`Issuer.VerifyToken`, the verifier introspection uses), requires its `aud` to name the client, decodes the user ID and connector ID from its `sub` and rebuilds the identity from its profile claims. Issuing for that identity reproduces the `sub`. This applies to impersonation and delegation alike; today a request without `connector_id` is refused, so nothing changes for existing clients.

Policy (`cmd/dex/config.go`):

```go
type DelegationPolicy struct {
	ClientID        string   `json:"clientID"`
	ActorConnectors []string `json:"actorConnectors"`
	Audiences       []string `json:"audiences"`
}
```

Loaded under `oauth2.tokenExchange.delegation` and validated at startup: one entry per client, `actorConnectors` non-empty and, when static connectors are configured, naming one of them (connectors kept in storage are resolved per request). The union of all `actorConnectors` is the set of actor connectors. `audiences` lists the cross-client audiences a delegated token may carry; empty means the client's own ID only.

Grant (`server/grants/tokenexchange.go`):

```go
if g.actorConnectors[req.ConnectorID] {
	return invalidRequest("connector only verifies actor tokens") // any client
}
policy, delegating := g.delegation[client.ID]
if !delegating {
	// impersonation, unchanged; actor_token was refused above
}
if client.Public { ... }
if req.ActorToken == "" {
	return invalidRequest("this client must present an actor_token")
}
if !slices.Contains(policy.ActorConnectors, req.ActorConnectorID) { ... }
for peer := range crossClientScopes(req.Scopes) {
	if !slices.Contains(policy.Audiences, peer) {
		return invalidTarget("audience not allowed for delegation")
	}
}
subjectIdentity, err := subjectConn.TokenIdentity(ctx, req.SubjectTokenType, req.SubjectToken)
subjectClaims, err := subjectConn.TokenClaims(ctx, req.SubjectTokenType, req.SubjectToken)
checkAudience(subjectClaims["aud"], client.ID)
if subjectClaims["act"] != nil {
	return invalidRequest("delegated subject tokens are not supported")
}
actorClaims, err := actorConn.TokenClaims(ctx, req.ActorTokenType, req.ActorToken)
checkAudience(actorClaims["aud"], client.ID)
checkMayAct(subjectClaims["may_act"], actorClaims)
auth.Act = &tokens.ActorClaims{Issuer: actorClaims["iss"], Subject: actorClaims["sub"]}
auth.ExpiresAt = min(subjectExp, actorExp)
```

`may_act` matching follows RFC 8693 Section 4.4: `sub` must match, and `iss` must match when `may_act` carries one.

Claims (`server/tokens`). `ActorClaims{Issuer, Subject}` is added to `IDTokenClaims` and `Authorization`; `Authorization` gains `ExpiresAt`. `SignIDToken` writes `act` and caps `exp`; access tokens are minted by the same function. `Introspection` gains a top-level `act` field, since access-token claims are otherwise decoded into the typed `ext` block.

### Observability

The existing "token exchange successful" log line gains `actor_connector_id`, `actor_iss` and `actor_sub`. Refusals log the reason. Raw tokens are never logged.

### Risks and Mitigations

- Actor token replay. The actor's `aud` must name the requesting client, so an actor token minted for another party or another client is refused. Dex does not track `jti`; the client can reuse an actor token until it expires, so actor tokens should be short-lived. The issued token never outlives the subject or actor token.
- Actor substitution. `actorConnectors` limits which issuers may act for a client, and the audience check limits which tokens. Unless the subject token carries `may_act`, nothing binds a given subject to a given actor: enabling delegation trusts the client to pair the subject and actor tokens it holds. The subject token must have been issued to the client (`aud`), so a token the client obtained for another party is refused; impersonation keeps today's behaviour (#4397).
- Consumers that ignore `act`. A delegated token presented to a backend that does not read `act` is served as the person alone, and the actor disappears. `audiences` restricts delegated tokens to the backends an operator knows read it; the client's own audience is always allowed. Operators grant `trustedPeers` to a delegating client for those backends only.
- Workload as subject. A connector listed in any `actorConnectors` is refused as `connector_id` for every client, so an actor token cannot be exchanged into a token whose `sub` is the workload.
- Privilege widening. The actor adds no scopes, audiences or groups.
- Laundering. A delegating client cannot exchange a subject token carrying `act`, so it cannot drop an existing chain. Clients without delegation keep today's behaviour.
- Public clients cannot delegate, since anything holding two tokens could mint a composite token in their name.
- Breaking change: none. Clients without a `delegation` entry and connectors not listed as actor connectors see the same behaviour and tokens.

### Alternatives

- Fields on `storage.Client`. Would reach clients created over gRPC and the Kubernetes CRD, but changes every storage backend. A server-level policy keyed by client ID covers static clients, where token-exchange clients are configured today, and can move later without changing semantics.
- Verify the actor token in the handler with a JWKS fetch. Bypasses the connector policy (`allowedConnectors`, `grantTypes`, custom CAs) the subject path already enforces.
- Let the gateway run its own token service. Backends then trust a second issuer, and the identity provider loses sight of the delegation.

## Future Improvements

- Issuing `may_act`, from a consent step, a connector claim or a policy source such as DEP "CEL integration" (#4601).
- A per-client `requireMayAct` switch, once subject issuers emit `may_act`.
- Delegation chains: accept a subject token carrying `act` and nest it under the new actor.
- Additional accepted actor audiences, and a subject audience check, per client.
- `access_token` actor and subject tokens, once a connector can return their verified claims.
- Returning `invalid_request` instead of `401 access_denied` for subject tokens that do not verify (RFC 8693 Section 2.2.2).
