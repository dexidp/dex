## Summary

Dex's token exchange ([RFC 8693]) accepts a `subject_token` and issues a Dex token for that subject.
This is impersonation in the sense of [RFC 8693 Section 1.1]: the issued token says nothing about who presented it.
This DEP adds delegation to the same grant.
A confidential client may also present an `actor_token`; Dex verifies it through a connector and issues one token whose `sub` is the subject and whose `act` claim names the actor.
When the subject token carries a `may_act` claim, Dex enforces it.
A subject token that is itself delegated can be exchanged again by a service with its own actor token, and Dex nests the earlier actor under the new one.
Delegated tokens carry their granted scopes in a `scope` claim.
Delegation is off unless an operator enables it per client, and clients without it see no change.

[RFC 8693 Section 1.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1

## Context

- [#5101] is the feature request this DEP answers.
- [DEP #2812] introduced token exchange and listed `actor_token` and `actor_token_type` as "OPTIONAL - unused".
  Its Future Improvements say they "can be checked / validated if a suitable use case is determined".
  This DEP supplies the use case and the validation.
- [#4910] split `/token` into per-grant handlers (`server/grants`) and [#4893] introduced `tokens.Issuer`.
  Delegation is added inside the token-exchange grant, the grant handler and the issuer, with no change to the other grants.
- [#4619] lets a connector be restricted to the grants it serves (`grantTypes`).
  An actor connector is a connector restricted to token exchange.
- [#4397] reports that id_token exchanges skip the `aud` check in the oidc connector.
  Delegation checks the actor token's audience in the grant, independent of that connector behaviour.
- [#3546] asks to refuse token exchange for public clients. Delegation refuses public clients from the start.
- [DEP #4600] / [#4611] (ID-JAG, open) propose a per-client policy under `oauth2.tokenExchange`.
  That block does not exist yet; this DEP introduces it with a `delegation` key, compatible with the ID-JAG proposal whichever lands first.

Use case. An agent runtime runs autonomous workloads on behalf of signed-in people.
Each workload has its own short-lived identity, a JWT minted by the runtime's issuer with a per-session subject.
A gateway in front of protected backends holds the person's token and the workload's actor JWT.
Backends need one bearer token that says "this person, acting through this workload", so they can authorize as the person and audit the workload.
Today the gateway must either forward the person's token alone (the workload becomes invisible) or run its own token service (a second issuer the backends must trust).
A backend that calls further services for the person must not forward the token it received; it needs its own token for each of them, and the workload must stay visible in it.

## Motivation

### Goals/Pain

- Accept `actor_token` and `actor_token_type` on the token-exchange grant ([RFC 8693 Section 2.1]), verified through a connector like the subject token.
- Issue the `act` claim ([RFC 8693 Section 4.1]) in ID tokens, access tokens and introspection responses.
- Enforce `may_act` ([RFC 8693 Section 4.4]) when the subject token carries it.
- Delegation chains ([RFC 8693 Section 4.1]): a subject token carrying `act` is exchanged with a new actor token, and its `act` is nested under the new actor.
- Issue the `scope` claim ([RFC 8693 Section 4.2]) and the `client_id` claim ([RFC 8693 Section 4.3]) in delegated tokens, so a consumer can enforce what the delegation was granted, as [RFC 8693 Section 5] suggests next to a limited lifetime.
- Per-client, operator-controlled enablement, including the audiences and scopes a delegated token may carry; no change for other clients.
- Exchange Dex-issued subject tokens, verified with Dex's own keys, keeping their `sub`.
  This is independent of delegation and also serves impersonation. It is part of this DEP because the use case needs it: the gateway holds a token Dex issued to it, and no connector can verify that token.

### Non-goals

- Issuing `may_act`. Dex has no source for "who may act for this subject".
- Impersonation through a delegating client. A client with a `delegation` entry always presents an actor; impersonation uses another client.
- `access_token` as actor token type, or as subject token type when a connector verifies the subject. The oidc connector verifies those through userinfo, so the token's own `aud`, `exp`, `act` and `may_act` are not available. A Dex-issued subject token is verified with Dex's keys and may be an access token.
- Per-client fields on the stored client object (`storage.Client`). See Alternatives.
- Refresh tokens for delegated tokens. Token exchange returns a single token today and keeps doing so.

## Proposal

### User Experience

Configuration. The actor's issuer is a connector restricted to token exchange. Delegation is enabled per client:

```yaml
connectors:
  - type: oidc
    id: corp                    # the connector people sign in through
    # ...
  - type: oidc
    id: agent-runtime
    name: Agent runtime
    config:
      issuer: https://issuer.agents.example.internal
    grantTypes:
      - urn:ietf:params:oauth:grant-type:token-exchange

oauth2:
  tokenExchange:
    delegation:
      - clientID: gateway
        actorConnectors: [agent-runtime]
        audiences: [backend-api]  # backends that read the act claim
        scopes: [tools:read]      # scope values the gateway may delegate

staticClients:
  - id: gateway
    secret: ...
  - id: backend-api
    # ...
    trustedPeers: [gateway]     # lets gateway request audience:server:client_id:backend-api
```

The actor connector only verifies the actor token's signature, issuer and expiry and returns its claims.
Its identity mapping (`userNameKey`, `email`, `groups`, userinfo) is not used, so a machine token needs no `name` or `email` claim.

Request. The client adds the actor token, its type and the connector that verifies it.
The subject token here is one Dex issued to the gateway, so no `connector_id` is sent and Dex verifies it with its own keys:

```sh
curl https://dex.example.com/token \
  --user gateway:secret \
  --data-urlencode grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  --data-urlencode subject_token=$PERSON_ID_TOKEN \
  --data-urlencode subject_token_type=urn:ietf:params:oauth:token-type:id_token \
  --data-urlencode actor_connector_id=agent-runtime \
  --data-urlencode actor_token=$WORKLOAD_TOKEN \
  --data-urlencode actor_token_type=urn:ietf:params:oauth:token-type:jwt \
  --data-urlencode scope="openid tools:read audience:server:client_id:backend-api" \
  --data-urlencode requested_token_type=urn:ietf:params:oauth:token-type:access_token
```

Response. One token, as today:

```json
{
  "iss": "https://dex.example.com",
  "sub": "CgdwZXJzb24xEgRjb3Jw",
  "aud": ["backend-api", "gateway"],
  "azp": "gateway",
  "client_id": "gateway",
  "exp": 1761150000,
  "scope": "openid tools:read",
  "act": {
    "iss": "https://issuer.agents.example.internal",
    "sub": "workload/session-7f3a"
  }
}
```

`sub` is the subject token's `sub` unchanged: a Dex-issued subject token is verified with Dex's keys and re-issued for the identity encoded in it. With `connector_id`, the subject token is verified by that connector as today and `sub` encodes its user ID and the connector.
A backend reads `sub` for authorization, `scope` for what the delegation may do, and `act` for audit. Only the audiences in the client's `audiences` list may be requested, because a consumer that does not read `act` would serve the token as the person alone.
`scope` lists the granted scopes except the cross-client `audience:server:client_id:` ones, which are expressed in `aud`. `client_id` names the client that requested the token, as `azp` does.
Dex gives the scope values no meaning; the consumer defines them. The client's `scopes` list bounds them: a delegating client may request Dex's standard scopes (`openid`, `email`, `profile`, `groups`, `federated:id`) and the values in its `scopes` list, nothing else.
The token response carries a `scope` parameter with the issued scopes, so the client sees what was granted without decoding the token ([RFC 8693 Section 2.2.1]).
The RFC 8693 `audience` and `resource` request parameters stay unsupported, as today. Dex expresses the target audience with the cross-client scope instead.

Chains. `backend-api` calls `reports-api` for the person. It must not forward the token it received, so it exchanges that token with its own workload token, verified by a connector for its platform's workload issuer:

```yaml
oauth2:
  tokenExchange:
    delegation:
      - clientID: gateway
        actorConnectors: [agent-runtime]
        audiences: [backend-api]
      - clientID: backend-api
        actorConnectors: [platform-workloads]
        audiences: [reports-api]
```

```sh
curl https://dex.example.com/token \
  --user backend-api:secret \
  --data-urlencode grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  --data-urlencode subject_token=$DELEGATED_TOKEN \
  --data-urlencode subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  --data-urlencode actor_connector_id=platform-workloads \
  --data-urlencode actor_token=$BACKEND_WORKLOAD_TOKEN \
  --data-urlencode actor_token_type=urn:ietf:params:oauth:token-type:jwt \
  --data-urlencode scope="audience:server:client_id:reports-api" \
  --data-urlencode requested_token_type=urn:ietf:params:oauth:token-type:access_token
```

The subject token is Dex-issued and names `backend-api` in its `aud`, so Dex verifies it with its own keys. The issued token nests the earlier actor under the new one ([RFC 8693 Section 4.1]):

```json
{
  "iss": "https://dex.example.com",
  "sub": "CgdwZXJzb24xEgRjb3Jw",
  "aud": ["reports-api", "backend-api"],
  "azp": "backend-api",
  "client_id": "backend-api",
  "exp": 1761150000,
  "scope": "",
  "act": {
    "iss": "https://kubernetes.default.svc",
    "sub": "system:serviceaccount:apps:backend-api",
    "act": {
      "iss": "https://issuer.agents.example.internal",
      "sub": "workload/session-7f3a"
    }
  }
}
```

The issued `scope` is a subset of the subject token's: scopes the subject does not carry are dropped. The request above asks for none beyond the audience, so the token carries an empty `scope`. A delegated token always carries `scope`, even empty, and a subject token that carries `act` but no `scope` claim is treated as having no scopes. Otherwise a hop that narrowed `scope` to nothing would look unrestricted to the next hop. `reports-api` authorizes the person and `backend-api` (the current actor); the workload is a prior actor, informational only.

Errors. Delegation refusals are `400 invalid_request` with a description, as RFC 8693 Section 2.2.2 requires for invalid or policy-refused actor tokens:

| Case | Description |
| --- | --- |
| `actor_token` and `actor_token_type` not sent together | "actor_token and actor_token_type must be sent together" |
| `actor_token` on any other grant | "actor_token is only valid for token exchange" |
| subject token not issued to the requesting client (`aud`) | "subject token audience does not include this client" |
| Dex-issued subject token does not verify | "invalid subject_token" |
| Dex-issued subject token whose session has ended | "subject token session has ended" |
| `audience` or `resource` sent by a delegating client | "audience and resource are not supported, use audience:server:client_id scopes" |
| client has no `delegation` entry, or is public, and sends `actor_token` | "delegation is not enabled for this client" |
| delegating client sends no `actor_token` | "this client must present an actor_token" |
| `connector_id` names an actor connector (any client) | "connector only verifies actor tokens" |
| unsupported actor or subject token type | "token type not supported for delegation" |
| a connector that cannot return verified claims | "subject connector does not support delegation" / "actor connector does not support delegation" |
| actor connector not in the client's `actorConnectors` | "actor connector not allowed for this client" |
| actor token does not verify | "invalid actor_token" |
| actor `aud` does not include the client ID | "actor token audience does not include this client" |
| subject token carries `act` and no `actor_token` is sent (any client) | "delegated subject tokens require an actor_token" |
| `may_act` present and not satisfied | "actor is not authorized by the subject token's may_act claim" |

A cross-client audience outside the client's `audiences` is refused with `400 invalid_target`, description "audience not allowed for delegation". [RFC 8693 Section 2.2.2] defines `invalid_target` for the `audience` and `resource` parameters; Dex uses it for the cross-client scope, which is how Dex expresses the same target.
A scope outside the standard scopes and the client's `scopes` is refused with `400 invalid_scope` ([RFC 6749 Section 5.2]), description "scope not allowed for delegation".

[RFC 8693 Section 2.2.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-2.2.1
[RFC 8693 Section 2.2.2]: https://www.rfc-editor.org/rfc/rfc8693.html#section-2.2.2
[RFC 6749 Section 5.2]: https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2

An actor connector outside the client's `allowedConnectors`, or without the token-exchange grant type, is refused by the existing connector check with its existing `invalid_grant` / `invalid_request` errors.

### Implementation Details/Notes/Constraints

Request and connector resolution (`server/grants/grants.go`). `Request` gains `ActorToken`, `ActorTokenType`, `ActorConnectorID`; `dispatch` rejects them on other grants.
`dispatch` resolves the actor connector with the same `resolveConnector` it uses for the subject connector, before `Authorize`, so the client's `allowedConnectors` and the connector's `grantTypes` apply to it.
The token-exchange grant receives it next to the subject connector and checks membership in `policy.ActorConnectors`.

Verified claims (`connector/connector.go`). `TokenIdentityConnector` returns an `Identity` only, so the grant never sees `aud`, `exp`, `may_act` or `act`. Add an optional interface:

```go
// TokenClaimsConnector verifies a signed token and returns the claims of the
// token itself, without userinfo or claim mapping applied.
type TokenClaimsConnector interface {
	TokenClaims(ctx context.Context, tokenType, token string) (map[string]any, error)
}
```

The oidc connector implements it for `id_token` and `jwt` with the provider's verifier and no client ID check, and never calls userinfo.
Delegation requires it on both connectors; the subject connector also keeps serving `TokenIdentity` for the subject's identity. Impersonation does not use it.

Dex-issued subject tokens (`server/tokens`, `server/grants/tokenexchange.go`). Without `connector_id`, the grant verifies the subject token with Dex's own signing keys, requires its `aud` to name the client, decodes the user ID and connector ID from its `sub` and rebuilds the identity from its profile claims. Issuing for that identity reproduces the `sub`.
The verification moves out of introspection's access-token check (`introspectAccessToken`) into a new `Issuer.VerifyToken`, used by both. It includes introspection's session check: when the subject token carries `sid` and the client binds its tokens to the session, a token whose session has ended is refused, and the issued token keeps that `sid`, so introspection reports it inactive once the session ends.
A subject token that does not verify is refused with `invalid_request`, as [RFC 8693 Section 2.2.2] requires; this path is new, so it does not inherit the `401 access_denied` of connector-verified subjects.
This applies to impersonation and delegation alike; today a request without `connector_id` is refused, so nothing changes for existing clients.

Delegated subjects. The grant reads the subject's claims whenever it can: always for a Dex-issued subject token, and for a connector-verified one when the connector implements `TokenClaimsConnector`. A subject carrying `act` is refused without an `actor_token`, for every client, so impersonation cannot drop an actor. With an actor token, the subject's `act` is nested under the new actor, and the issued token keeps the subject's other limits: its `scope` bounds the issued `scope`, and its `exp` bounds the issued `exp`. A delegated subject without a `scope` claim bounds the issued `scope` to nothing.

Policy (`cmd/dex/config.go`):

```go
type DelegationPolicy struct {
	ClientID        string   `json:"clientID"`
	ActorConnectors []string `json:"actorConnectors"`
	Audiences       []string `json:"audiences"`
	Scopes          []string `json:"scopes"`
}
```

Loaded under `oauth2.tokenExchange.delegation` and validated at startup: one entry per client, `actorConnectors` non-empty and, when static connectors are configured, naming one of them (connectors kept in storage are resolved per request). The union of all `actorConnectors` is the set of actor connectors. `audiences` lists the cross-client audiences a delegated token may carry; empty means the client's own ID only. `scopes` lists the scope values a delegated token may carry beyond Dex's standard scopes; empty means the standard scopes only. `scopes` may not contain `audience:server:client_id:` values, which `audiences` governs.

Grant (`server/grants/tokenexchange.go`):

```go
if g.actorConnectors[req.ConnectorID] {
	return invalidRequest("connector only verifies actor tokens") // any client
}
policy, delegating := g.delegation[client.ID]
if !delegating {
	// impersonation, unchanged; actor_token was refused above
}
if client.Public { ... }
if req.ActorToken == "" {
	return invalidRequest("this client must present an actor_token")
}
if req.Audience != "" || req.Resource != "" {
	return invalidRequest("audience and resource are not supported, use audience:server:client_id scopes")
}
if !slices.Contains(policy.ActorConnectors, req.ActorConnectorID) { ... }
for peer := range crossClientScopes(req.Scopes) {
	if !slices.Contains(policy.Audiences, peer) {
		return invalidTarget("audience not allowed for delegation")
	}
}
for _, s := range otherScopes(req.Scopes) { // neither standard nor cross-client
	if !slices.Contains(policy.Scopes, s) {
		return invalidScope("scope not allowed for delegation")
	}
}
subjectIdentity, err := subjectConn.TokenIdentity(ctx, req.SubjectTokenType, req.SubjectToken)
subjectClaims, err := subjectConn.TokenClaims(ctx, req.SubjectTokenType, req.SubjectToken)
checkAudience(subjectClaims["aud"], client.ID)
actorClaims, err := actorConn.TokenClaims(ctx, req.ActorTokenType, req.ActorToken)
checkAudience(actorClaims["aud"], client.ID)
checkMayAct(subjectClaims["may_act"], actorClaims, client.ID)
auth.Act = &tokens.ActorClaims{
	Issuer:  actorClaims["iss"],
	Subject: actorClaims["sub"],
	Act:     decodeAct(subjectClaims["act"]), // nil unless the subject is delegated
}
// A subject without act or scope leaves req.Scopes unchanged; a subject with
// act and no scope bounds them to the cross-client scopes only.
auth.Scopes = withinSubjectScope(req.Scopes, subjectClaims["scope"], subjectClaims["act"] != nil)
auth.ExpiresAt = min(subjectExp, actorExp)
```

The `Request` also gains `Audience` and `Resource`, read only to refuse them on delegating clients.

The impersonation path gains one check before it issues: `if subjectClaims["act"] != nil { return invalidRequest("delegated subject tokens require an actor_token") }`, where the subject's claims are available.

`may_act` matching. [RFC 8693 Section 4.4] defines the claim but leaves matching to the authorization server, and allows it to name either the client or the party in the actor token. Dex's rule:

- `sub` must equal the actor token's `sub`, and `iss`, when present, the actor token's `iss`.
- `client_id` must equal the requesting client's ID.
- `may_act` must carry `sub` or `client_id`, and `iss` only together with `sub`.
- Any other member refuses the exchange, since Dex cannot tell an identifying member from an informational one.

Claims (`server/tokens`). `ActorClaims{Issuer, Subject, Act *ActorClaims}` is added to `IDTokenClaims` and `Authorization`; `Authorization` gains `ExpiresAt`. `SignIDToken` writes `act` with any nested chain, writes `scope` (empty when no scopes remain) and `client_id` for delegated tokens, and caps `exp`; access tokens are minted by the same function. `SignIDToken` returns the capped expiry, so `expires_in` in the response matches the token. The token-exchange response sets `scope` to the issued scopes for delegated exchanges ([RFC 8693 Section 2.2.1] requires it whenever they differ from the request). `Introspection` gains a top-level `act` field and fills its existing `scope` field from the token's `scope` claim, since access-token claims are otherwise decoded into the typed `ext` block.

### Observability

The existing "token exchange successful" log line gains `actor_connector_id`, `actor_iss`, `actor_sub` and, for chains, `prior_actor_sub`. Refusals log the reason. Raw tokens are never logged.

### Risks and Mitigations

- Actor token replay. The actor's `aud` must name the requesting client, so an actor token minted for another party or another client is refused. Dex does not track `jti`; the client can reuse an actor token until it expires, so actor tokens should be short-lived. The issued token never outlives the subject or actor token.
- Actor substitution. `actorConnectors` limits which issuers may act for a client, and the audience check limits which tokens. Unless the subject token carries `may_act`, nothing binds a given subject to a given actor: enabling delegation trusts the client to pair the subject and actor tokens it holds. The subject token must have been issued to the client (`aud`), so a token the client obtained for another party is refused; impersonation keeps today's behaviour (#4397).
- Consumers that ignore `act`. A delegated token presented to a backend that does not read `act` is served as the person alone, and the actor disappears. `audiences` restricts delegated tokens to the backends an operator knows read it; the client's own audience is always allowed. Operators grant `trustedPeers` to a delegating client for those backends only.
- Workload as subject. A connector listed in any `actorConnectors` is refused as `connector_id` for every client, so an actor token cannot be exchanged into a token whose `sub` is the workload.
- Privilege widening. The actor adds no scopes, audiences or groups. At the first hop, the client's `scopes` and `audiences` bound what it can request; Dex does not check them against what the person consented to, so an operator lists only the scopes the client may exercise for anyone it serves. In a chain, the issued `scope` is a subset of the subject token's, a delegated subject without `scope` counts as having none, and `exp` never passes the subject's.
- Signed-out sessions. A Dex-issued subject token whose session has ended is refused, and the issued token keeps the subject's `sid`, so ending the session also deactivates the delegated token at introspection. Consumers that validate the JWT locally keep accepting it until `exp`, as they do for any Dex token.
- Policy on prior actors. In a chain, consumers apply access control to `sub` and the outermost `act` only; nested actors are informational ([RFC 8693 Section 4.1]). Limits on an earlier actor are enforced by the party that actor called directly, and carried on through `scope`.
- Laundering. A subject token carrying `act` is only accepted together with an `actor_token`, and its `act` is nested in the issued token, never dropped. Without an `actor_token` (impersonation) it is refused for every client, whenever the subject's claims are available: always for Dex-issued subject tokens, and for connector-verified ones whose connector implements `TokenClaimsConnector`.
- Chain length. RFC 8693 sets no limit and neither does this DEP. Each hop needs a delegating client and a verified actor token issued to it, and every hop can only narrow `scope` and `exp`.
- Public clients cannot delegate, since anything holding two tokens could mint a composite token in their name.
- Breaking change: one refusal. An impersonation exchange of an external subject token that carries `act`, through a connector that now implements `TokenClaimsConnector` (the oidc connector), is refused where it used to drop the `act`. Otherwise clients without a `delegation` entry, and connectors not listed as actor connectors, see the same behaviour and tokens.

### Alternatives

- Fields on `storage.Client`. Would reach clients created over gRPC and the Kubernetes CRD, but changes every storage backend. A server-level policy keyed by client ID covers static clients, where token-exchange clients are configured today, and can move later without changing semantics.
- Verify the actor token in the handler with a JWKS fetch. Bypasses the connector policy (`allowedConnectors`, `grantTypes`, custom CAs) the subject path already enforces.
- Let the gateway run its own token service. Backends then trust a second issuer, and the identity provider loses sight of the delegation.

## Future Improvements

- Issuing `may_act`, from a consent step, a connector claim or a policy source such as DEP "CEL integration" (#4601).
- A per-client `requireMayAct` switch, once subject issuers emit `may_act`.
- A per-client bound on chain depth, if operators ask for one.
- Additional accepted actor audiences, and a subject audience check, per client.
- `access_token` actor and subject tokens, once a connector can return their verified claims.
- Returning `invalid_request` instead of `401 access_denied` for connector-verified subject tokens that do not verify (RFC 8693 Section 2.2.2).
- Supporting the RFC 8693 `audience` and `resource` parameters, mapped to cross-client scopes.
