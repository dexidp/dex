## Summary

Dex's token exchange ([RFC 8693]) accepts a `subject_token` and issues a Dex token for that subject.
This is impersonation in the sense of [RFC 8693 Section 1.1]: the issued token says nothing about who presented it.
This DEP adds delegation to the same grant.
A confidential client may also present an `actor_token`; Dex verifies it through a connector and issues one token whose `sub` is the subject and whose `act` claim names the actor.
When the subject token carries a `may_act` claim, Dex enforces it.
So that the subject keeps the identifier backends already know, Dex also accepts its own tokens as subject tokens and keeps their subject unchanged.
Delegation is off unless an operator enables it per client.

[RFC 8693]: https://www.rfc-editor.org/rfc/rfc8693.html
[RFC 8693 Section 1.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1

## Context

- [#5101] is the feature request this DEP answers.
- [DEP #2812] introduced token exchange and listed `actor_token` and `actor_token_type` as "OPTIONAL - unused".
  Its Future Improvements say they "can be checked / validated if a suitable use case is determined".
  This DEP supplies the use case and the validation.
- [#4910] split `/token` into per-grant handlers (`server/grants`) and [#4893] introduced `tokens.Issuer`.
  Delegation is added inside the token-exchange grant, the grant handler and the issuer, with no change to the other grants.
- [#4619] lets a connector be restricted to the grants it serves (`grantTypes`).
  An actor connector is a connector restricted to token exchange.
- [#4780] added the structured success log for token exchange; this DEP extends that line.
- [#4397] reports that id_token exchanges skip the `aud` check in the oidc connector.
  Delegation checks the actor token's audience in the grant, independent of that connector behaviour.
- [#3546] asks to refuse token exchange for public clients. Delegation refuses public clients from the start, the same rule `client_credentials` applies.
- [DEP #4600] / [#4611] (ID-JAG, open) propose a per-client policy under `oauth2.tokenExchange`.
  That block does not exist yet; this DEP introduces it with a `delegation` key and keeps its shape compatible with the ID-JAG proposal, whichever lands first.

Use case. An agent runtime runs autonomous workloads on behalf of signed-in people.
Each workload has its own short-lived identity, a JWT minted by the runtime's issuer with a per-session subject.
A gateway in front of protected backends holds the person's Dex token and the workload's actor JWT.
Backends need one bearer token that says "this person, acting through this workload", so they can authorize as the person, audit the workload, and tell a human call from an agent call.
Today the gateway must either forward the person's token alone (the workload becomes invisible) or run its own token service (a second issuer the backends must trust).
RFC 8693 delegation at the identity provider is the standard answer.

## Motivation

### Goals/Pain

- Accept `actor_token` and `actor_token_type` on the token-exchange grant ([RFC 8693 Section 2.1]), verified through a connector like the subject token.
- Issue the `act` claim ([RFC 8693 Section 4.1]) in ID tokens, access tokens and introspection responses, with nesting when the subject token already carries `act`.
- Enforce `may_act` ([RFC 8693 Section 4.4]) when the subject token carries it.
- Accept Dex-issued tokens as subject tokens and keep their `sub`, so a delegated token names the person with the same identifier as their other Dex tokens.
- Per-client, operator-controlled enablement.

### Non-goals

- Issuing `may_act`. Dex has no source for "who may act for this subject"; see Future Improvements.
- Actor tokens of type `access_token`. The oidc connector verifies those through userinfo, so the token's own `aud`, `exp` and `may_act` are not available.
- Delegation with `access_token` subject tokens from a connector, for the same reason.
- Per-client fields on the stored client object (`storage.Client`). See Alternatives.
- Refresh tokens for delegated tokens. Token exchange returns a single token today and keeps doing so.
- Resource and audience parameters of RFC 8693 Section 2.1.1, out of scope since DEP #2812.

[RFC 8693 Section 2.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-2.1
[RFC 8693 Section 4.1]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1
[RFC 8693 Section 4.4]: https://www.rfc-editor.org/rfc/rfc8693.html#section-4.4

## Proposal

### User Experience

Configuration. The actor's issuer is a connector restricted to token exchange. Delegation is enabled per client:

```yaml
connectors:
  - type: oidc
    id: agent-runtime
    name: Agent runtime
    config:
      issuer: https://issuer.agents.example.internal
      userNameKey: sub          # machine tokens carry no "name" claim
    grantTypes:
      - urn:ietf:params:oauth:grant-type:token-exchange

oauth2:
  tokenExchange:
    delegation:
      - clientID: gateway
        actorConnectors: [agent-runtime]
        # actorAudiences: [https://dex.example.com]   # optional; the client's own ID is always accepted
        # requireMayAct: false                        # default; true refuses subjects without may_act

staticClients:
  - id: gateway
    secret: ...
    trustedPeers: [backend-api]
```

Request. The client sends the person's Dex token as the subject (no `connector_id`, since Dex verifies its own tokens), and adds the actor token, its type and the connector that verifies it:

```sh
curl https://dex.example.com/token \
  --user gateway:secret \
  --data-urlencode grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  --data-urlencode subject_token=$PERSON_TOKEN \
  --data-urlencode subject_token_type=urn:ietf:params:oauth:token-type:id_token \
  --data-urlencode actor_connector_id=agent-runtime \
  --data-urlencode actor_token=$WORKLOAD_TOKEN \
  --data-urlencode actor_token_type=urn:ietf:params:oauth:token-type:jwt \
  --data-urlencode scope="openid audience:server:client_id:backend-api" \
  --data-urlencode requested_token_type=urn:ietf:params:oauth:token-type:access_token
```

Response. One token, as today. Its payload, for a person who signed in through a connector `github`:

```json
{
  "iss": "https://dex.example.com",
  "sub": "CgdwZXJzb24xEgZnaXRodWI",
  "aud": ["backend-api", "gateway"],
  "azp": "gateway",
  "exp": 1761150000,
  "act": {
    "iss": "https://issuer.agents.example.internal",
    "sub": "workload/session-7f3a"
  }
}
```

`sub` is the same value as in the person's own Dex tokens.
A backend reads `sub` for authorization and `act` for audit; per RFC 8693 Section 4.1 it considers only the top-level claims and the outermost `act`.

Errors. Every refusal is `400 invalid_request` with a description, as RFC 8693 Section 2.2.2 requires for invalid or policy-refused subject and actor tokens. Client authentication failures keep their existing `invalid_client` response.

| Case | Description |
| --- | --- |
| `actor_token` without `actor_token_type`, or the reverse | "actor_token and actor_token_type must be sent together" |
| `actor_token_type` is not `id_token` or `jwt` | "actor_token_type not supported for delegation" |
| `actor_token` on any other grant | "actor_token is only valid for token exchange" |
| client has no `delegation` entry | "delegation is not enabled for this client" |
| client is public | "delegation requires a confidential client" |
| `actor_connector_id` missing, not in `actorConnectors`, or refused by `allowedConnectors` / `grantTypes` | "actor connector not allowed for this client" |
| subject `connector_id` is one of the client's `actorConnectors` | "connector is an actor connector for this client" |
| subject token from a connector is an `access_token`, or the connector cannot return verified claims | "subject token type not supported for delegation" |
| actor token does not verify | "invalid actor_token" |
| actor `aud` names neither the client ID nor an `actorAudiences` entry | "actor token audience does not include this client" |
| subject `may_act` present, actor does not match | "actor is not authorized by the subject token's may_act claim" |
| subject has no `may_act` and `requireMayAct` is true | "subject token carries no may_act claim" |
| resulting `act` chain deeper than 10, or an `iss` / `sub` in it longer than 255 bytes | "delegation chain too large" |
| verified subject token carries `act` and no `actor_token` is sent | "subject token is delegated; present an actor_token" |
| Dex-issued subject token does not name the client in `aud` | "subject token was not issued to this client" |

A subject token that does not verify keeps today's response. Its use of `401 access_denied` predates this DEP and also departs from Section 2.2.2; aligning it is left to a separate change so that this DEP does not alter the impersonation responses.

### Implementation Details/Notes/Constraints

Request (`server/grants/grants.go`). `Request` gains `ActorToken`, `ActorTokenType`, `ActorConnectorID`. `Handler.dispatch` rejects any of them on a grant other than token exchange.

Actor connector resolution (`server/grants/grants.go`). `resolveConnector` is a `Handler` method that runs before `Authorize`, so no grant can skip the connector checks. The actor connector goes through the same path: an optional grant interface

```go
// actorGrant is implemented by grants that accept a second, actor connector.
type actorGrant interface {
	ActorConnectorID(ctx context.Context, req *Request, client storage.Client) (string, *oauth2.Error)
}
```

lets `dispatch` resolve the actor connector with `resolveConnector`, which applies the client's `allowedConnectors` and the connector's `grantTypes`, and pass it to the grant next to the subject connector.
The token-exchange grant checks membership in `policy.ActorConnectors`.

Verified claims (`connector/connector.go`). `TokenIdentityConnector` returns an `Identity` only; the grant never sees `iss`, `aud`, `exp`, `may_act` or `act` of either token. Add an optional interface:

```go
// TokenClaimsConnector verifies a signed token and returns the identity together
// with the verified claims the identity was derived from.
type TokenClaimsConnector interface {
	TokenIdentityClaims(ctx context.Context, tokenType, token string) (Identity, map[string]any, error)
}
```

The claims are those of a verified signature, never a userinfo response.
The oidc connector implements it for `id_token`, and for `jwt` when called for an actor token; `jwt` is not accepted as a subject token type.
go-oidc does not distinguish an ID token from another JWT by its `typ` header, so the two types are verified the same way and the audience check below is what keeps an actor token from being any token the issuer signed.
The mock connector implements it with a configurable claims map.
A connector without it can still serve impersonation; a delegation request through it, as subject or actor connector, is refused.

Dex-issued subject tokens (`server/grants/tokenexchange.go`). When `connector_id` is absent (refused today), the subject token must be an ID or access token signed by Dex itself, verified with Dex's own keys as the userinfo and introspection endpoints do.
Its `aud` must name the requesting client, so a client can only exchange tokens issued to it or naming it as a trusted peer.
The issued token keeps the subject's `sub`: the grant decodes the subject's `(user ID, connector ID)` and passes them on, so `GenSubject` reproduces the same value.
Claims (`email`, `groups`, `name`, `preferred_username`) come from the subject token, so the issued token can only carry claims the subject token carried.
This path serves impersonation and delegation alike.

Policy (`cmd/dex/config.go`, `server/grants/delegation.go`):

```go
type DelegationPolicy struct {
	ClientID        string   `json:"clientID"`
	ActorConnectors []string `json:"actorConnectors"`
	ActorAudiences  []string `json:"actorAudiences"`
	RequireMayAct   bool     `json:"requireMayAct"`
}
```

`OAuth2` gains `TokenExchange struct{ Delegation []DelegationPolicy }`, loaded under `oauth2.tokenExchange.delegation`, validated at startup (`actorConnectors` must be non-empty and name configured connectors; a client ID appears once), and passed to `grants.Handler`.

Grant (`server/grants/tokenexchange.go`), after the subject is verified:

```go
policy, delegating := g.delegation[client.ID]
if delegating && slices.Contains(policy.ActorConnectors, req.ConnectorID) {
	return invalidRequest("connector is an actor connector for this client")
}
if req.ActorToken == "" {
	if subjectClaims["act"] != nil { // only known for verified signed subject tokens
		return invalidRequest("subject token is delegated; present an actor_token")
	}
	// impersonation, otherwise unchanged
}
if !delegating || client.Public { ... }
if subjectClaims == nil { // access_token subject or connector without TokenClaimsConnector
	return invalidRequest("subject token type not supported for delegation")
}
actorIdentity, actorClaims, err := actorConn.(connector.TokenClaimsConnector).TokenIdentityClaims(ctx, req.ActorTokenType, req.ActorToken)
checkAudience(actorClaims["aud"], client.ID, policy.ActorAudiences)
checkMayAct(subjectClaims["may_act"], actorClaims, policy.RequireMayAct)
act := &tokens.ActorClaims{Issuer: actorClaims["iss"], Subject: actorClaims["sub"], Act: nestedFrom(subjectClaims["act"], subjectClaims["iss"])}
if act.Depth() > maxActDepth || act.TooLong(maxActValueLen) { ... }
auth.Act = act
auth.ExpiresAt = min(subjectExp, actorExp) // zero keeps the configured lifetime
```

`may_act` matching follows RFC 8693 Section 4.4: `sub` must match, and `iss` must match when `may_act` carries one. Other claims inside `may_act` are not compared in this version.

Nested chains. `nestedFrom` copies the subject token's `act` chain under the new actor. An entry without `iss` is relative to the subject token's issuer; once Dex re-signs it, a missing `iss` would read as relative to Dex, so `nestedFrom` sets the subject token's `iss` on such entries. Only `iss`, `sub` and `act` are copied from each entry. The chain is bounded at 10 levels and each `iss` and `sub` at 255 bytes; larger chains are refused rather than truncated.

Claims (`server/tokens/claims.go`, `issuer.go`):

```go
type ActorClaims struct {
	Issuer  string       `json:"iss,omitempty"`
	Subject string       `json:"sub"`
	Act     *ActorClaims `json:"act,omitempty"`
}
```

`IDTokenClaims` and `tokens.Authorization` gain `Act *ActorClaims`; `Authorization` gains `ExpiresAt time.Time`. `SignIDToken` writes `act` and caps `exp`. Access tokens are minted by the same function, so both token types carry `act`. `act` is never copied into `federated_claims`.

Introspection (`server/introspection/introspection.go`). Access-token claims are decoded into the typed `IntrospectionExtra` under `ext`, which would drop `act`. `Introspection` gains a top-level `Act *tokens.ActorClaims` field filled from the verified access token, as RFC 8693 Section 4.1 describes for introspection responses.

Scopes and audience are untouched: the actor contributes no scope and no audience; `aud` comes from the client and its cross-client scopes as today.

### Observability

The existing "token exchange successful" log line gains `actor_connector_id`, `actor_iss`, `actor_sub`, `may_act_enforced` and `act_depth`. Refusals log the reason with the same keys. Raw tokens are never logged.

A counter `dex_token_exchange_delegation_total{client_id, result, reason}` counts delegation outcomes, with `reason` taken from a fixed set matching the error table, so refusal spikes are visible without log parsing.

### Risks and Mitigations

- Actor token replay from another relying party. An actor token minted for some other audience must not turn into a Dex delegation. The grant requires the actor's `aud` to name the requesting client's ID or an operator-listed `actorAudiences` entry; the check lives in the grant and does not depend on the connector's audience handling (#4397). Defaulting to the client ID binds an actor token to one client: another client sharing the same actor connector cannot use it. An operator who lists a shared audience, such as the Dex issuer URL, in `actorAudiences` gives up that binding for that client.
- Actor token replay within its lifetime. Dex does not track actor `jti` values, so the client the token was minted for can reuse it until it expires. Actor tokens should be short-lived; the issued token never outlives the actor token.
- Actor substitution. A client could pair a person's token with any actor token its actor connectors verify. The operator's `actorConnectors` list says which issuers may act for that client at all, and the audience check says which actor tokens were minted for it. `may_act`, when the subject token carries it, binds the subject to one actor. With `requireMayAct: false` (the default, since Dex and most identity providers do not issue `may_act`), the client is trusted to combine any subject token and any actor token it holds; enabling delegation for a client is that grant of trust. `requireMayAct: true` is for deployments whose subject issuer emits `may_act`.
- Actor connector used as a subject connector. A connector listed in a client's `actorConnectors` is refused as that client's subject connector, so a workload token cannot be exchanged into a token whose `sub` is the workload and that carries no `act`.
- Privilege widening. The actor adds nothing: no scopes, no audiences, no groups. The issued token's lifetime is the shortest of the configured lifetime, the subject token and the actor token.
- Chain size. Nested `act` is bounded at 10 levels and 255 bytes per `iss` / `sub`; larger requests are refused rather than truncated.
- Confused deputy through a public client. Public clients cannot delegate; a public client's secret is public, so anything holding two tokens could mint a composite token in its name.
- Laundering a delegated token. A verified subject token that carries `act` cannot be exchanged without an actor: dropping the chain would turn a delegated token into an impersonation token, and copying it forward would assert an actor that did not authenticate in this request (RFC 8693 Section 4.1 makes the outermost `act` the current actor). The check needs the subject token's signed claims, so it covers Dex-issued subject tokens and `id_token` subjects from connectors implementing `TokenClaimsConnector`. It cannot see `act` in `access_token` subjects, which the oidc connector verifies through userinfo, or in tokens from connectors without that interface; those keep today's behaviour and delegation through them is refused.
- Exchanging someone else's Dex token. A Dex-issued subject token is accepted only when its `aud` names the requesting client, the same rule a resource server applies.
- Personal data in logs. The log line carries identifiers (`actor_sub`, existing `user_id`, `email`), as the current exchange log does, and never tokens. The metric carries no user identifiers.
- Behaviour change for existing clients. Two changes reach clients that send no actor parameters:
  - An exchange whose verified subject token carries `act` is refused, for every client, whether or not delegation is configured. Today such a token is exchanged and its chain is silently dropped. This is a deliberate security fix and needs a release note.
  - A request without `connector_id`, refused today, now exchanges a Dex-issued subject token.

  Every other impersonation request, its response and its token are unchanged. The new connector interface is optional.

### Alternatives

- Fields on `storage.Client`. First-class per-client fields would reach clients created over gRPC and the Kubernetes CRD, but every storage backend changes (ent schema and SQL migration, Kubernetes types, `api.proto`, conformance tests), as `allowedConnectors` did across about 35 files. A server-level policy keyed by client ID has the same effect for static clients, which is where token-exchange clients are configured today, and can move into the client object later without changing semantics.
- Verify the actor token in the handler with a JWKS fetch. Shorter, but it bypasses connector policy (`allowedConnectors`, `grantTypes`, custom CAs, discovery overrides) that the subject path already enforces. Delegation reuses the connector path for the actor token.
- Exchange the person's Dex token through an oidc connector pointing at Dex itself. Works with no new code, but the issued `sub` encodes that connector and the original subject together, so it no longer matches the person's other Dex tokens and backends cannot authorize on it.
- Gate the laundering check behind delegation being configured. Keeps impersonation fully unchanged, but leaves every other client able to strip an `act` chain by exchanging the token.
- Let the gateway run its own token service. Backends then trust a second issuer, and the person's identity provider loses sight of the delegation. RFC 8693 places this at the authorization server.
- Do nothing. Deployments keep forwarding person tokens alone, or minting composite tokens outside Dex. DEP #2812 left this open for a use case; the use case exists.

## Future Improvements

- Issuing `may_act`: from a consent step, a connector-supplied claim, or a policy source such as the CEL work in DEP "CEL integration" (#4601). Today's enforcement is designed so issuance can be added without changing the exchange.
- Actor tokens of type `access_token`, and delegation with `access_token` subjects from connectors, verified through introspection of the issuer once the connector can return the token's verified claims for that type.
- Allowing `jwt`-type subject tokens generally, and letting the new `jwt` connector (#5083) serve as an actor connector by implementing `TokenClaimsConnector`.
- Comparing further identity claims inside `may_act` (RFC 8693 Section 4.4 allows claims beyond `sub` and `iss`).
- Returning `invalid_request` instead of `401 access_denied` for subject tokens that do not verify, as RFC 8693 Section 2.2.2 requires.
